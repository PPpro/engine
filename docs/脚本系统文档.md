# 脚本系统文档

一个引擎真正意义上的脚本系统，应该只设计并服务于实现项目侧业务逻辑用的，他使用的语言可以是 ts，可以是 lua，可以是蓝图，甚至可以类似 godot 一样的自研语言 GDScript。  
脚本系统 和 ts 脚本 是两个概念，但是由于我们引擎主要技术栈是 ts，所以 ts 脚本 和 脚本系统 相关的工作常常被混淆在一起。  
我们的引擎实际上还没有一个真正意义上成熟的脚本系统，充其量只能算是一个依附 js 生态的开发环境，而这个生态的边界本身就没有足够清晰，他把 node modules 带进来了，把 DOM 带进来了，关于前端的一切都可以被带进来，而我们对这些能力的开放缺少把控，脚本系统最终只能跟着前端的那一套标准跑，而且停不下来。  
所以这篇文档与其说是 脚本系统，更确切的应该是涵盖了整个 ts 语言体系的相关工作流说明。  

这一块主要会分为两点：
- 构建工具
- 运行时模块系统

## 构建工具

由于历史原因，构建工具被实现为多套，分散在仓库各地，主要涉及以下几个仓库：
- 项目构建
    - programming 项目脚本开发时编译：https://github.com/cocos/cocos-editor/tree/develop/app/builtin/programming 这是一个编辑器扩展插件，他核心实现是通过 asset-db-interop 来监听 db 的消息，由 db 的消息来发起编译请求，通知 packer-driver 来处理可能并发的编译请求
    - build-script 项目脚本发布时构建：https://github.com/cocos/cocos-editor/blob/develop/app/builtin/builder/source/worker/builder/asset-handler/script/build-script.ts 主要依赖 rollup 以及 creator-programming-rollup-plugin-mod-lo 插件
    - creator-programming: https://github.com/cocos/creator-programming, 这是一个提供脚本构建能力的基础库，不涉及上层的业务。该仓库被实现为一个 monorepo，意味着这个完整的库是由多个子库构成的，这样的好处是能够尽量复用子库代码，子库包括： 
        - creator-programming-babel-preset-cc: 这是一个 babel preset，里边是一些预设给 cocos 使用的 babel 插件集。请记住仓库的 `preset-for-engine` 分支, 这个是早期给引擎定制过的一个装饰器优化版本，升级版本需要人力，所以暂时单独建一个分支给引擎编译使用，主干分支是给项目脚本编译使用的。这是早期仓库管理混乱遗留的版本依赖问题。他的前身是这个仓库 https://github.com/cocos-creator/cocos-babel-preset-cc ，目前可能还有部分实现还依赖这个废弃仓库。
        - creator-programming-common: 一些通用的工具库
        - creator-programming-import-maps: 支持 import-map 的模块解析 （import-map 是一个前端的模块映射标准，参考 https://developer.mozilla.org/en-US/docs/Web/HTML/Element/script/type/importmap ）
        - creator-programming-mod-lo: 核心模块 module loader，这里涉及到脚本编译的模块解析，脚本编译，这里就包括了对 npm 模块的支持相关逻辑
        - creator-programming-rollup-plugin-mod-lo: 将 creator-programming-mod-lo 封装为 rollup 插件，给其他 rollup 构建工具使用，比如上面提到的 build-script
        - creator-programming-quick-pack: 主要提供 build 接口，驱动 mod-lo 编译
        - creator-programming-test-utils：私有模块，不对外发布，用于本地做 unit test 的一些测试工具
    
- 引擎构建
    - quick-compiler: https://github.com/cocos/cocos-editor/tree/develop/packages/quick-compiler, 这是引擎开发时的构建工具，满足开发时快速构建的需求，核心的思路是他的构建输出是散文件，可以充分利用这些散文件的 mtime 或者 hash 来做增量编译，这里区别于 vite 的运行时按需编译，增量编译更适合 cocos 的需求。
    - 重点介绍一下 ccbuild https://github.com/cocos/cocos-ccbuild ，他的定位是 **Cocos Creator 完整的构建解决方案**，包括项目构建和引擎构建。这是 [维护文档](https://github.com/cocos/cocos-ccbuild/blob/master/README_MAINTAIN.md)。目前是只支持了引擎发布时构建，未来他需要覆盖的包括：引擎开发时、发布时构建，项目开发时、发布时构建，引擎 dts 构建, 引擎文档构建。也就是以上提到的所有的构建仓库，最终都应该合并到 ccbuild。目前已有的模块包括：
        - build-engine 引擎的构建工具，目前包括 2 个后端 js-engine, ts-engine(给 OH 平台 AOT 使用)，未来需要合并 quick-compiler
        - dts-bundler 构建 cc.d.ts，这里需要提到另一个基础库 gift https://github.com/shrinktofit/gift 目前是李楠个人的私有仓库，有需要可以 fork 到 cocos 官方仓库
        - modularize 支撑引擎模块化相关基础设施，引擎模块化相关的设计参考 [文档](TODO)
        - stats-query 引擎信息查询
        - bundler 汇集所有可能的打包工具后端，目前包括 rollup，未来可以加入 esbuild，webpack，turbopack 等，编辑器都统一使用该模块导出的接口，避免重复安装打包工具，相关 issue: TODO
        - transformer 汇集所有可能的编译工具后端，目前包括 babel，typescript，未来可以加入 swc，编辑器都统一使用该模块导出的接口，避免重复安装编译工具，相关 issue: TODO
    - build-engine: https://github.com/cocos/cocos-engine/tree/develop/packages/build-engine 这是一个废弃的仓库，目前大部分能力已经迁移到了 ccbuild，不过有部分引擎的 CI 目前还依赖 build-engine 的接口，暂时保留了，未来可以考虑移除
- 文档构建
    - typedoc-plugin: https://github.com/cocos/cocos-engine/tree/develop/packages/typedoc-plugin 引擎执行 `npx typedoc` 生成 json 数据
    - api 文档：http://git.cocos.org:9080/G_Engine/cocos3d-docs-api 这个是编辑器前端组在维护的项目，由引擎 `npx typedoc` 生成的 json 数据投喂给他生成前端 api 文档页面

## 运行时模块系统

模块系统最核心是使用 SystemJS 作为主要的模块规范，参考 https://github.com/systemjs/systemjs ，SystemJS 是 ESM 模块机制的一个 js 实现，使用它有以下这些好处：
- 完全对标 ESM 的能力，不管是 dynamic import，top level await, 还是 live binding, SystemJS 都能满足需求
- 由 js 实现，不依赖浏览器或者小游戏宿主原生提供的模块规范，具有更高的兼容性和跨平台能力
- 不管什么平台，我们的 js 构建产物可以做到统一为 SystemJS 模块
- 可以更灵活满足其他定制需求，比如模块热更

就像 Babel 能够通过插件扩展的机制来支持 JS 的一些前沿的语法特性，SystemJS 也可以通过扩展来支持前沿的 ESM 模块规范提案。

由于历史原因，模块系统也被实现为多套，分散在仓库各地。目前包括：
- cocos-module-system 基于 SystemJS 实现的 cocos 模块系统 https://github.com/cocos/cocos-module-system ，已经应用于编辑器 [构建](https://github.com/cocos/cocos-editor/blob/develop/app/builtin/builder/source/worker/builder/asset-handler/script/index.ts) 和 [预览](https://github.com/cocos/cocos-editor/blob/develop/app/builtin/preview/source/programming/Facet.ts)。这个是目前主推的仓库，之后所有相关仓库都应该合并到 cocos-module-system
- editor-systemjs https://github.com/cocos/cocos-editor/tree/develop/packages/lib-programming/src/editor-systemjs ，用于编辑器内执行脚本，这是 lib-programming 库下的一个子模块，也是基于 SystemJS 封装的一个给编辑器使用的模块系统，[executor](https://github.com/cocos/cocos-editor/blob/develop/packages/lib-programming/src/executor/index.ts) 是对他一个更上层业务的封装。lib-programming 其实最开始是设计用来支撑所有编译工作的基础库，只是后来各项业务被拆分出去了，包括拆分到了 creator-programming，目前遗留下来最核心的实现就是 executor 部分，这部分之后也应该合并到 cocos-module-system 里，之后就可以移除 lib-programming 了。

### 引擎模块与编辑器模块交互

这块目前的实现我觉得是比较 hack 的，原因在于编辑器是跑在 CommonJS 模块下的，而引擎是跑在 SystemJS 模块下。
SystemJS 的模块导入是一个异步操作，CommonJS 的导入是一个同步操作。

目前这块的解决方案是在编辑器启动阶段提前完成引擎 SystemJS 模块的异步加载，之后 CommonJS 在加载引擎模块的时候，是从模块缓存里去取模块的，这样就把异步操作变成了一个同步操作。参考：https://github.com/cocos/cocos-editor/blob/develop/app/builtin/engine/modules/cc/preload.ts  
不同模块的交互性也应该是 cocos-module-system 要解决的问题，相关 issue: https://github.com/cocos/3d-tasks/issues/9710

### 题外话
由于 SystemJS 源码使用 js 实现，本身代码不够健壮。最近有在尝试用 ts 去重构 cocos-module-system, 这个是目前处于 WIP 的重构分支 https://github.com/cocos/cocos-module-system/tree/refactor 。重构后的 cocos-module-system 应该会更合理一些，增加了 pal 部分的实现，因为模块系统底层也有一些平台的差异需要抹平，比如：
- 小游戏和编辑器是 CommonJS，web 是 script 标签加载
- 不同平台对于 globalThis 的处理也不尽相同，比如淘宝平台的 globalThis 就只能在模块内局部访问，不能缺省

抹平这些差异后，我们的启动流程模板就可以做到更加统一，不用再每个平台写一套 `System.warmup`，甚至淘宝平台也不需要在脚本的文件头增加那么多恶心的 `var xxx = $global.xxx;` 的写法，这些都是对用户不友好的。欢迎感兴趣的有缘人可以继续完善这部分的实现并最终投入生产环境。


## 总结

脚本系统的所有工作，最终都会围绕构建工具和模块系统两大块展开。未来期望所有的工作，都在 ccbuild 和 cocos-module-system 里完成，把其他仓库移除掉。

不要再增加仓库了 ！！！
